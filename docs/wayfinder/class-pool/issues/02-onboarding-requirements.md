# 02 — What does the generator need before it can roll an occult class?

Type: grilling
Status: resolved (2026-08-03) -- answered by the build; see feature_spec_todo.md section 10
Blocked by: 01 (resolved)
Map: [Class pool](../map.md)

## Question

Deleting a name from `occult_classes` (`Backend/utils/data.py:2381`) is a one-line change and would
be wrong on its own — the class would roll and then generate a character with no features, no
choices, and nothing on either sheet. **What is the complete list of things that must exist before a
class name can safely leave that list?**

The deliverable is a **checklist**, reusable per class, that ticket 03 then applies to decide who
ships.

### The surface to enumerate

Walk the pipeline in `Backend/main_test.py` order and name every place a class must appear. From
charting, the known ones:

- **`Backend/utils/data.py`** — casting stat (`int_casters`/`wis_casters`/`cha_casters`, `:285-287`)
  and good saves (`:2393-2400`) are **already populated for all eight**. Still unverified: hit die,
  BAB progression, skill ranks per level, class skill list, starting wealth, and whether
  `base_classes` (`:171`) is the list a new class must join.
- **`Backend/json/class_data/<class>.json`** — the per-class data file every chooser reads via
  `getattr(character, class_1, {})`. Whether these exist for the occult six is unknown at charting.
- **Spell/power progression** — the occultist, medium, mesmerist, psychic and spiritualist all cast;
  which existing progression do they attach to, and does the spell chooser already handle a
  spontaneous-with-a-known-list caster of that shape?
- **The choice pools** — see below.
- **`data.amount` or its successor** — the pick schedule for whatever they choose. Note that
  [Map: Class choices](../../class-choices/map.md) ticket 01 may replace this table wholesale; this
  ticket should name the *requirement* ("a schedule must exist"), not the file, so the answer
  survives that decision.
- **The Foundry module and the web sheet** — a bucket that no renderer knows about is invisible; the
  psionics invariant's own comment calls this failure "generated but invisible".

### The split that matters most

**These six are not one job.** Some are a data-shape add — a `class_data` file and a schedule entry,
and the existing choosers handle them unchanged. Others are a **bespoke engine**:

- **kineticist** — burn (an HP-cost resource), wild talents, infusions, elemental focus. Nothing in
  the generator resembles burn, and `data.py:288` already records that the caster map cannot express
  it.
- **occultist** — implements and mental focus: a pool of points reallocated per day across chosen
  implement schools, with resonant vs. focus powers. Two coupled choices, not one list.
- **medium** — spirits are a *daily* choice, not a build choice. The generator emits a static
  snapshot; a class whose central feature changes every morning may not fit that shape at all.
- **spiritualist** — the phantom is companion-shaped and may want a row in
  `Backend/json/companion_grantors.json` rather than a chooser.
- **mesmerist** (tricks, mesmerist stares) and **psychic** (discipline, phrenic amplifications) look
  like the ordinary "pick N from a list" shape the existing choosers already serve.

**§9 Psionics is the yardstick.** Twelve classes landed there, and nine of them needed *no new chooser
module* — `generic_class_option_chooser` handled every subsystem, with the option lists generated by
`Backend/scripts/build_psionic_class_data.py` and the schedules hand-read into `data.amount`. Decide
for each occult class whether it lands on the psionics side of that line or genuinely needs new code,
and say what the tell is.

### What "resolved" looks like

A checklist with a per-item "where it lives" pointer, plus a first-pass grading of the six classes as
**data-shape add** / **bespoke engine** / **does not fit the snapshot model at all**, with the reason.
Ticket 03 turns that grading into a ship list; this ticket does not decide who ships.
